# ChunkRace — Scoring Engine: System Documentation

This document describes the internal behavior of the A2 scoring service: what it receives, how it processes submissions, what it returns, and how data is persisted. Intended for anyone integrating a client against this service (frontend, test scripts, the RAG starter kit).

## 1. Overview

```
Participant / Frontend
      │
      │  POST /submit  (answers generated by the participant's RAG pipeline)
      ▼
┌─────────────────────────────────────────┐
│         FastAPI service (A2)             │
│                                           │
│  1. Check submission count for           │
│     this participant (anti-oracle)       │
│  2. Score each answer (semantic          │
│     similarity vs. expected answer)      │
│  3. Classify each answer into a zone     │
│     (pass / gray / fail)                 │
│  4. Aggregate into score + breakdown     │
│  5. Persist to SQLite                    │
│  6. Return the aggregated result         │
└─────────────────────────────────────────┘
      │
      │  GET /leaderboard  (read-only, polling recommended client-side)
      ▼
   Sorted ranking
```

The service never generates an answer itself — it only **compares** an answer already produced by the participant to an expected answer supplied by Person A1.

## 2. Embedding model

- Current model: `all-MiniLM-L6-v2` (via `sentence-transformers`) — **placeholder**. Must be replaced with whichever model Person B's RAG starter kit uses, so both sides operate in the same vector space and similarity scores stay meaningful.
- Similarity is cosine similarity between the embedding of the expected answer and the embedding of the generated answer, producing a score in roughly [0, 1] for natural language text.
- The model is loaded once, at import time, inside `engine.py`. Loading it requires a Hugging Face Hub lookup unless `HF_HUB_OFFLINE=1` is set and the model is already cached locally (see README for the offline setup recommended on event day).

## 3. Decision zones

| Zone | Condition | Handling |
|---|---|---|
| `pass` | score ≥ 0.75 | Automatically accepted |
| `gray` | 0.60 ≤ score < 0.75 | Flagged for human review (Person A1's review grid) — escalation flow not yet defined |
| `fail` | score < 0.60 | Automatically rejected |

Thresholds (0.75 / 0.60) are currently calibrated on placeholder examples only. They must be recalibrated once the real dataset from Person A1 is available.

## 4. Dataset loading

Expected answers are no longer hardcoded in the service. They are loaded from `data/expected_answers.json` at service startup:

```json
{
  "q1": "Les téléphones sont interdits en examen.",
  "q2": "La pause dure quinze minutes."
}
```

Format: a flat object mapping `question_id` to the expected answer text. The service loads this file once when it starts (`@app.on_event("startup")`) — it is not re-read per request. To swap in the real dataset, replace the file's contents (or point `load_expected_answers()` at a different path) and restart the service.

## 5. Endpoints

### `GET /health`

Liveness check.

**Response**

```json
{"status": "ok"}
```

### `POST /submit`

Submits a participant's answers for evaluation.

**Request**

```json
{
  "participant_id": "p1",
  "answers": {
    "q1": "Non, les téléphones sont interdits en examen.",
    "q2": "La pause dure quinze minutes."
  }
}
```

- `participant_id`: identifier for the participant.
- `answers`: a `{question_id: generated_answer}` mapping. Keys should match the question IDs defined in `data/expected_answers.json`.

**Response (success)**

```json
{
  "participant_id": "p1",
  "score": 2,
  "total": 2,
  "zone_breakdown": {"pass": 2, "gray": 0, "fail": 0},
  "submission_number": 1,
  "submitted_at": "2026-07-29T00:13:51.182003+00:00"
}
```

- `score`: number of questions landing in the `pass` zone (i.e. number of questions answered correctly, per the spec's definition of "score").
- `total`: total number of questions evaluated.
- `zone_breakdown`: aggregated counts per zone — **never** per-question detail (anti-oracle constraint).
- `submission_number`: this submission's rank for the participant (1 or 2).
- `submitted_at`: UTC timestamp, used as the leaderboard tie-breaker.

**Response (limit reached — HTTP 429)**

```json
{"detail": "Submission limit reached (2 max)."}
```

What the API never returns: the score or zone of an individual question. A client cannot infer which specific question failed from the response.

### `GET /leaderboard`

Returns the current ranking across all participants who have submitted at least once.

**Response**

```json
[
  {"participant_id": "p1", "score": 2.0, "submitted_at": "2026-07-29T00:13:51.182003+00:00"},
  {"participant_id": "p2", "score": 1.0, "submitted_at": "2026-07-29T00:25:20.228502+00:00"}
]
```

- Sorted by score descending, then by timestamp ascending on ties.
- Only each participant's **best submission** (out of up to 2) is included; the associated timestamp is that of the best-scoring submission, not necessarily the participant's first attempt.
- Recommended client usage: poll this endpoint periodically. No push mechanism (WebSocket) is implemented.

## 6. Anti-oracle mechanism

Two protections work together:

1. **Submission limit**: 2 maximum per `participant_id`. The count check and increment happen under a lock scoped to that participant, closing the race condition where two near-simultaneous requests could otherwise both read "count = 1" before either writes "count = 2", letting a 3rd submission slip through.
2. **Opacity of detail**: per-question scores exist only transiently, in memory, for the duration of a single request. They are never persisted individually and never returned to the client — only the aggregated `zone_breakdown` is stored and returned. A participant cannot deduce which specific question they got wrong to target their second attempt.

## 7. Data model (SQLite persistence)

Table `submissions`:

| Column | Type | Description |
|---|---|---|
| `id` | INTEGER (primary key) | Auto-incrementing identifier |
| `participant_id` | TEXT | Participant identifier |
| `score` | REAL | Number of questions passed |
| `total` | INTEGER | Total number of questions |
| `pass_count` | INTEGER | Number of answers in the `pass` zone |
| `gray_count` | INTEGER | Number of answers in the `gray` zone |
| `fail_count` | INTEGER | Number of answers in the `fail` zone |
| `submitted_at` | TEXT (ISO 8601) | UTC timestamp of the submission |

One row = one full submission. Per-question detail never exists in this table at any point.

Storage uses a local SQLite file (`submissions.db`) rather than in-memory state, so the submission history survives a service crash or restart during the event.

## 8. Ranking logic

- For each participant, `best_submission` picks the submission with the higher score; ties are broken by the earlier timestamp.
- `rank_participants` then sorts one best-submission-per-participant list by score descending, timestamp ascending on ties.
- This two-level comparison is intentional: the first level picks a participant's own best attempt, the second level resolves cross-participant ties at the leaderboard level.

## 9. Deployment notes for event day

- Pre-download the embedding model before event day; set `HF_HUB_OFFLINE=1` when running the service so it never depends on Hugging Face Hub availability during the event.
- CORS must be configured to allow the frontend's origin before it can call this service from a browser — not yet implemented.
- A file-based fallback path (JSON submissions dropped via USB / shared folder, processed manually through the same engine) is planned for network outages during the event, but not yet implemented or tested.

## 10. Open dependencies

- **Embedding model**: final choice depends on Person B's starter kit.
- **Real dataset**: depends on Person A1; will replace `data/expected_answers.json`.
- **CORS origin**: depends on where the frontend is hosted.
- **`zone_breakdown` response format**: proposed as compliant with the anti-oracle rule in the spec, but not yet confirmed with Person A1.
